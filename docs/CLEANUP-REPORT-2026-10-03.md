# LOGOX 清理与流畅性优化验收（2026-10-03）

状态：已实现并通过离线验收，随 `codex/anamnesis` 分支提交交付。清理测量基线：`cc60781`；`main` 未改。2026-10-05 时间戳联动和本批交付进度见 [架构 §11](ARCHITECTURE.md#11-接手顺序与当前进度)，本报告保留 2026-10-03 清理阶段的独立测试和测量结果。设计依据见 [清理设计](CLEANUP-DESIGN-2026-10-03.md)。

## 1. 结果与适用范围

本轮检查了 118 个 Python 源文件的引用与死代码候选，并沿输入、事件、渲染、工具执行、上下文和持久化链路检查阻塞点。完成保持现有功能的优化：复用未变排版结果、减少流式缓冲复制、修正两个交互状态问题、移出文件工具的只读准备计算，并清理有明确证据的旧实现和误生成文件。

全量验收：**2068 passed / 3215 subtests passed，89.90 秒**。源码、新增测试和基准脚本 Ruff 检查通过，Git 差分空白检查通过。相对基线新增 34 项测试；不使用耗时阈值作为单测通过条件。测试证明覆盖场景的行为，性能测量另列下文。

本轮没有连接真实模型或改动真实会话／记忆内容；LEGACY 未读取或修改。保留默认主屏终端历史、全屏阅读锚点、权限审批、压缩恢复、六工具接口、插件入口和入梦规则。

## 2. 卡顿原因与改动

### 2.1 历史没变，仍反复做同一份工作

旧流程虽然缓存了消息排版，仍在每帧重建片段列表、行区间和完整行列表；Screen 又重新检查所有行的格宽。历史越长，敲一个字也要处理越多对象。全屏滚动条还会复制可见行，使未变行错过后续 ANSI 序列化缓存。

现在 [timeline.py](../src/logox/tui/content/timeline.py) 保留未变前缀的片段与区间，只重建变化后缀；[app.py](../src/logox/tui/render/app.py) 复用对应平坦行列表；[screen.py](../src/logox/tui/render/screen.py) 复用同一宽度、同一不可变 Text 行的格宽检查结果；[fullscreen.py](../src/logox/tui/render/fullscreen.py) 复用可见行和滚动条字符／样式的组合结果。

仍逐块检查真实显示内容键，确保较早工具状态或正文原地变化能显示；中文格宽、选择、主题和缩放不能为了提速跳过。缓存只保留当前数据，清空和结构变化释放旧结果。整帧并非恒定成本，尚未实现只排版视口内消息的虚拟化。

### 2.2 展开一张卡片，却清空整个历史缓存

Ctrl+T / Ctrl+O 原先调用整段失效，普通正文也重新解析和排版。现在展开开关只进入对应种类的内容键：思考／入梦或工具／Diff；单卡点击同样按实际 expanded 状态失效。主题、宽度和清空仍执行必要失效，阅读锚点按原规则恢复。缓存键也包含入梦卡片对象及 revision，避免同版本号的新卡片错误复用旧正文。

### 2.3 流式积压每释放一点，都复制剩余全文

[smoother.py](../src/logox/tui/content/smoother.py) 原来的字符串切片在每步释放最多 16 字符后复制全部剩余积压。积压越大，重复复制越严重。现在正文和推理各自使用分段队列、头片段偏移和剩余字符计数，每步只复制本次释放的部分；公开接口、步长、字符顺序和终态排空保持原规则。

这减少 CPU 与分配成本，不提高模型生成速度，也不消除终端写出阻塞。普通每帧仍最多释放 16 字符，大积压在终态仍会排空。

### 2.4 两处交互状态错误

- [editor.py](../src/logox/tui/render/components/editor.py)：补全成功后的历史索引重置位于 return 之后，永远不执行。从历史草稿接受补全后，上下键可能回到旧选择；重置移到返回前，加入真实键序列测试。
- [app.py](../src/logox/tui/render/app.py)：ModelRequestFinished 只代表一次模型请求结束，一轮任务可能继续执行工具、重试或补写摘要。忙状态现在持续到整轮终态，避免这段间隙允许 reload／模型或会话变更穿过既有守卫。

### 2.5 edit/write 准备工作占住界面执行时间

[fs_edit.py](../src/logox/tools/fs_edit.py) 的读取、匹配、Diff、编码计算，以及 [fs_write.py](../src/logox/tools/fs_write.py) 的既有文件统计，改为只读工作线程准备。等待时界面事件循环可以处理其他任务；返回后再次检查取消，后台准备不写源文件。edit 提交前比较当前文件与准备时原始字节，外部修改会得到要求重新 read 的明确失败，不覆盖该修改。

没有把整个写工具扔进后台：否则用户已经看到取消，后台却仍可能修改文件。临时文件写入、replace、最终内容核对及调度器快照仍有同步成本；线程也不能保证所有 Python 计算完全不争用解释器。内容核对与替换不是针对外部程序的不可分割事务，权限策略也不等于操作系统沙箱。

## 3. 同机性能复测

### 3.1 方法

Windows、Python 3.11.15、FakeTerminal 100×30，合成中文 Markdown 历史。每对历史由一条用户消息与一条助手消息组成。相同脚本分别在基线与最终工作区运行；每场景 15 帧，表中单位均为 **ms，中位数**。输入与流式表计时从 render_now 开始，不包含按键到达或网络传输；样本较少，不能解读为真实 P99 延迟。

FakeTerminal 不包含 Windows Terminal / ConPTY 的输入、尺寸查询、真实写出、历史重排或绘制；也不包含模型服务、网络、上下文构建及磁盘工具操作。以下只能说明对应离线路径的成本变化。

## 4. 测试覆盖

新增 [TUI 测试](../tests/tui/test_cleanup_performance.py) 与 [工具准备测试](../tests/unit/test_tool_preparation.py)，共 34 项。重点不是重新断言代码怎么写，而是验证这些后果：

- 未变行不重复宽度检查；新对象和缩放重新检查，清空释放缓存。
- 缓存与无缓存渲染在固定随机操作、原地修改、删除、重排、宽度及展开变化下，正文和样式一致；分块与完整 Text 兼容入口可切换。
- 空片段不会多出空行；中文窄宽度、输入法光标与复用缓存不会污染原始行。
- 滚动条未变行保留身份，主题和新行变化正确失效；快捷键只重排相关卡片，入梦卡片替换不会误命中。
- 正文／推理交错和大积压不丢字，flush／clear 保持原契约。
- 模型请求结束仍然忙，整轮成功／失败／取消才解锁；补全后的历史键序列正确。
- task.cancel 或工具取消标志发生在后台准备期间，源文件不变、无写回临时文件；准备异常不报成功；edit 拒绝覆盖中途外部修改。

完整测试还覆盖权限、回滚、厂商适配、压缩恢复、入梦、插件和 MCP 的已有行为。为适配当前执行环境，只在测试进程移除继承的 HTTP_PROXY／HTTPS_PROXY／ALL_PROXY，并把临时目录创建模式 0700 替换为普通模式；不改变用户环境、产品代码、权限配置或既有文件 ACL。

## 6. 模块审计与剩余问题

| 模块 | 本轮结果 | 仍存在的边界 |
|---|---|---|
| 01 内核 | 轮次和工具终态、取消契约通过回归；修复界面过早解锁 | 事件订阅者的同步工作仍可能阻塞事件发布链路 |
| 02 上下文 | 删除旧私有封装；保留有效压缩状态恢复与极小窗口本地策略 | 大上下文构建、状态序列化和持久化仍有成本，未测真实百万 token 请求 |
| 03 TUI | 缓存复用、展开局部失效、平滑器优化、补全修复 | 仍扫描内容键及差分行，未做完整视口虚拟化；真实终端写出待测 |
| 04 模型适配 | 现有异步流与厂商契约保留，通过回归 | 分片频率和首 token 延迟受模型服务影响，本轮未作实际 Qwen 对照 |
| 05 工具 | edit/write 只读准备卸载；edit 漂移检查；grep 保持异步 rg | 同步提交、快照和部分 Python CPU 运算仍可能停顿；读取不是有界流式解析 |
| 06 权限 | 清理类型与等价分支，保留所有审批及路径规则 | 应用策略无法提供 OS 沙箱；检查与执行间仍存在外部替换窗口 |
| 07 存储 | 核查日志与压缩恢复，纠正文档持久性描述 | JSONL／context_state／CAS 的同步写入和崩溃一致性仍值得单独设计 |
| 08 装配与扩展 | 整轮忙守卫、依赖及动态入口保留 | reload 仍有既有边界；不能为“死代码”删除外部 SDK／插件接口 |
| 09 入梦 | 保留调度、唤醒、归属及恢复规则，改善卡片缓存 | 本地模型的语义质量、记忆召回与实际长任务终端体验尚未量化 |

下一阶段先做两件事，不直接更换业务语义：

1. **真实终端定位剩余停顿**：分别测按键到达、消息显示、上下文构建、事件订阅者、尺寸查询与终端 write 的耗时。只记录时长和规模，不记录聊天正文。依据瓶颈决定投入，避免把服务分片不均匀误判为渲染问题。本轮没有增加常驻追踪或遥测。
2. **评审存储与界面解耦**：候选是单一写入执行者按事件顺序保存，再明确退出／取消排空、成功确认、错误回报和压缩状态的提交时机。它可能进一步减轻磁盘卡顿，但直接把写入丢给线程会破坏顺序或恢复保证，不能作为无行为变化的清理擅自实施。

若内容键／行扫描在更长历史中仍占主导，再讨论视口渲染与显式版本管理；代价是点击范围、滚动锚点和原地修改契约都需重做，不能只删除检查。

## 7. 面试时怎样说明

**缓存失效（cache invalidation）**：问题是每次打字重复排版长历史；全部缓存又会让旧工具状态停在“运行中”。本项目按实际显示键验证变化，复用未变前缀，只在对应卡片展开、宽度／主题或内容变化时重排。这是面试常考的，追问重点是怎样证明没有显示陈旧数据；答案是缓存与无缓存输出对拍、旧块原地变更和边界测试，而非只报提速数字。

**协作式取消（cooperative cancellation）**：问题是界面已经显示取消，后台线程却可能继续写文件。准备线程因此只读，返回后检查取消，写回保持在明确提交区间；线程仍可能继续算，只是没有写入副作用。这是面试常考的，追问“取消协程是否等于停止线程”，本项目的答案是否定的。

**轮次终态（turn terminal state）**：一次模型请求结束不等于用户任务结束；模型可能接着调工具。界面忙状态应跟随整轮终态，否则中途重载／切换会制造不一致。这里没有添加新状态机，而是修正既有状态使用的事件边界。

讲成果可以引用第 3 节的固定离线场景和第 4 节测试；不要把它写成真实用户延迟、token 节省、工具调用减少或召回准确率提升，这些尚无本轮证据。
