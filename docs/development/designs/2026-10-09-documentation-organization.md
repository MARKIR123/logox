# LOGOX 文档组织与持续维护设计

日期：2026-10-09。状态：已完成文档整理与静态验收；当前修改未提交。

适用工作区：LOGOX 当前工作目录，分支 `codex/anamnesis`。本次盘点包含尚未提交的源码与文档；整理时以当时工作树的实际行为核对，不能把分支提交状态当成全部实现状态。

## 1. 问题与目标

当前模块文档混入旧实现、修改原因、排查过程、阶段测试计数和未解释的 Dxxx 编号。README、PRD、界面规范、设计和验收材料重复描述用户行为，改动后容易出现互相矛盾的说明。架构文档同时承担长期架构说明和不断追加的接手历史。

目标是让读者明确回答三类问题：如何使用 LOGOX；当前实现如何工作；重要设计为何如此、典型问题如何解决。当前说明持续改写，历史材料带时间定位，普通修改由 Git 保存。

本次只整理文档及其维护规则，不改变 LOGOX 的运行行为。

## 2. 已确认的决策与取舍

| 已确认方案 | 未采用方案 | 理由与代价 |
|---|---|---|
| 两类读者、三种内容职责 | 严格两套文档，将实现原理与使用说明混放 | 用户说明、当前实现、开发历史分别回答不同问题；需要明确导航与归属。 |
| Git 保存普通修改，文档保存重要决策与典型复盘 | 每次修改都追加模块演进记录 | 降低重复维护；提交说明仍需记录问题、变动和验证。 |
| 保留 `docs/modules/`，增加 `user/` 与 `development/` | 将全部材料搬入两棵新目录 | 保持现有模块入口，减少迁移与链接修复。 |
| 设计完成后保留带日期、状态和提交关联的记录 | 完成后删除设计，只通过 Git 查找 | 便于理解设计理由；历史设计必须明确适用时间与后继记录。 |
| 按改动影响分级文档工作量 | 所有修改都创建完整设计文档 | 保留先文档后代码，普通修复使用简短修改说明。 |
| 当前 PRD 持续维护 | 仅靠 README 和分散设计表示整体范围 | 保留统一产品边界，具体操作和机制通过链接说明。 |
| 当前接手状态独立到 `STATUS.md` | 继续写入架构文档 | 状态更新频繁，架构更新较少；完成事项移出当前清单。 |
| 正式工程文档随代码管理，私人材料本地保存 | 工程决策和复盘继续混在本地忽略文档中 | 支持项目交接；迁移前需要区分私人原文与可共享材料。 |
| 使用简短的分类模板，章节按需调整 | 完全自由写法 | 帮助识别遗漏；不要求填充无意义的空章节。 |
| 非 LEGACY 旧历史原文保留，精选整理 | 全部旧历史逐条规范化 | 保留追溯能力，把整理精力用于有长期价值的记录。 |
| AGENTS 保留核心规则、沟通偏好和读取条件 | 全部开发细节常驻 AGENTS | 减少每次会话的加载内容；详细指南的读取条件必须明确。 |
| 概念定义融入 PRD、架构或所属模块 | 另设独立术语文档 | 减少阅读入口；产品概念由 PRD 定义，实现相关概念在架构或模块中就近解释。 |

上述目录选择容易调整，不需要为文档目录本身另外创建架构决策记录。

## 3. 目录与职责

以下是已整理的职责结构。历史目录按实际材料创建，不预建空目录。新增文档须有独立的职责或读取场景；现有文档能够清楚承载的内容优先合并为章节，不为模板或技能约定额外增加文件。

```text
LOGOX/
├── README.md
├── AGENTS.md
└── docs/
    ├── README.md
    ├── PRD.md
    ├── ARCHITECTURE.md
    ├── UI-SPEC.md
    ├── user/                      用户操作与故障处理
    ├── modules/                   当前机制、接口与边界
    ├── development/
    │   ├── WORKFLOW.md
    │   ├── TESTING.md
    │   ├── STATUS.md
    │   ├── designs/
    │   ├── decisions/
    │   ├── reviews/
    │   └── research/
    └── legacy/                    旧文档日期归档（本地忽略）
```

用户本轮指定旧文档归入 `docs/legacy/2026-10-09-documentation-refresh/`，保持原目录结构并保存哈希清单；既有 legacy 目录不读取、不修改。原始审计材料归档后不参与当前事实核对。正式手册不依赖归档材料才能读懂。

### 3.1 根目录与全局文档

| 文档 | 职责 |
|---|---|
| `README.md` | 简介、最短上手路径、用户与开发者文档入口；详细教程使用链接。 |
| `AGENTS.md` | 先文档后代码、交互式需求讨论、授权边界、LEGACY 排除规则、必须生效的沟通偏好，以及按任务读取文档的条件。 |
| `docs/README.md` | 按读者与任务组织导航，说明当前文档与历史记录的区别。 |
| `docs/PRD.md` | 当前产品定位、目标用户、产品概念、能力范围、范围边界与主要验收目标；规划能力与已实现能力明确区分。 |
| `docs/ARCHITECTURE.md` | 当前分层、模块协作、依赖方向、关键数据流、架构概念和跨模块约束；当前任务转到 STATUS。 |
| `docs/UI-SPEC.md` | 当前布局、组件、视觉与交互约束，面向实现者；操作步骤交给用户指南。 |

### 3.2 用户说明

`docs/user/` 按实际篇幅组织快速开始、配置、命令与快捷键、权限与恢复、Anamnesis、主题和常见故障。允许先合并相关主题，内容增长后再拆分。

说明以用户能执行的步骤、看到的结果和真实限制为主。配置值、命令和键位核对当前注册逻辑与默认配置；不从旧设计直接复制成现行指令。

### 3.3 当前模块说明

保留现有九篇模块文档及 `docs/modules/README.md`。模块数量随职责演进，不固定为八个或九个。

每篇至少包含：定位与边界、当前机制与数据流、关键接口与关系、失败边界与限制、源码和验证入口。已有五节模板可以调整为这些必要内容，不必为了固定结构重复正文。

源码入口以稳定路径和符号名为主；只有解释接口所需的小片段才复制进正文。完整签名、配置列表和测试列表能直接查到时，优先链接其维护位置。

正文中的当前取舍允许简短解释其影响；完整方案比较、旧实现和排查过程放到历史记录。临时缺陷和待办以 STATUS 为入口，模块只解释持续成立的边界并按需引用。

### 3.4 开发指南与当前状态

| 文档 | 必要内容 |
|---|---|
| `WORKFLOW.md` | 环境准备、需求讨论、设计、实现、验证、文档同步及提交要求；明确文档归属与修改分级。 |
| `TESTING.md` | 测试运行方法、不同测试的用途、覆盖边界、真实终端和模型的验收方式。配置与脚本作为执行依据，不复制某次通过数量作为永久基线。 |
| `STATUS.md` | 当前未完成任务、已知问题、阻塞条件、下一步及设计、提交、验证入口。注明最近核对日期与适用工作状态；完成事项移出，历史由提交或复盘保存。 |

面向下一会话的临时交接只引用以上文件，补充尚未沉淀的必要信息，不再创建一份长期状态副本。

### 3.5 历史记录

| 目录 | 内容与最小结构 |
|---|---|
| `designs/` | 问题与目标、范围、方案比较、确认方案、接口和边界、验收条件；注明日期和状态，完成后关联实际提交与后继设计。 |
| `decisions/` | 当时的问题、选择、主要替代方案、理由和接受的代价。仅保存难以推翻、缺少上下文会令人困惑且经过真实取舍的重要决策。 |
| `reviews/` | 典型问题的现象、假设、证据、根因、修改、验证及遗留问题；重要验证报告注明当时环境、代码状态、方法和结果。 |
| `research/` | 调研问题、来源、调查日期、结论与限制；外部材料不会自动成为 LOGOX 的产品约束。 |

历史文件采用有意义的标题，文件名可用 `YYYY-MM-DD-topic.md`。链接用可理解的标题；编号仅作为定位补充，不以 D151 一类编号代替完整规则。

历史中的正确描述保持其时间语境。补充勘误时注明补充日期；后续推翻设计或决策时另建记录并互相关联，不将当时结论静默改写成今天的结论。

## 4. 持续维护流程

1. 修改前读取所属模块当前说明。遇到产品行为、技术路线或交互选择未确定时，先逐轮讨论；事实由源码和环境核对。
2. 新功能、行为变化和架构重构先形成对应设计，明确失败边界和验收条件，确认后实现。普通缺陷修复先留下简短问题、修改和验证说明，不强制另建完整设计文件；可放在任务说明、已有设计的适用修订处或 STATUS 中，完成后不继续占据当前清单。
3. 实现后改写受影响的当前说明，移除失效说法。跨模块行为明确由哪个模块负责，其他文档从各自读者角度说明或引用，不再各维护一份完整机制。
4. 根据改动影响同步用户指南、PRD、架构或 UI 规范；未受影响的文档无需为制造维护痕迹而更新。
5. 当前文档注明有意义的核对日期和适用范围；只能证明离线行为的材料不写成真实终端或模型已验收。
6. Git 提交描述普通修改的问题、变化和验证；重要取舍或典型排查才形成独立历史记录。设计完成后标记状态与实际落地位置。
7. 收尾更新 STATUS 的剩余事项，校验受影响链接和引用；下一会话从当前入口继续，不依赖翻阅全部历史。

AGENTS 中保留上述流程的核心要求，并提供明确指引：需求或行为变更读 WORKFLOW 和相关设计；代码修改读所属模块；验证读 TESTING；接手或收尾读 STATUS；产品概念变化读 PRD，架构与实现概念变化读 ARCHITECTURE 或所属模块。沟通偏好仍留在 AGENTS，详细通用流程下放指南。每个概念在所属文档中维护定义，其他位置按需引用，不另设术语文件。

工程文档中的个人信息、会话原文和本机特有路径在进入可共享记录前剔除或泛化。项目运行生成的 `ANAMNESIS.md`、会话日志和状态文件继续按运行数据管理，不纳入工程手册。

## 6. 执行顺序与边界

本轮按以下顺序执行：

1. 保存本地原文，建立文档入口、开发流程与维护约定。
2. 核对并改写 PRD、架构、界面规范和 STATUS。
3. 对照当前源码逐模块整理，再由真实行为提炼用户指南。
4. 精选历史设计、决策、复盘和调研，整理测试指南。
5. 同步 AGENTS 和忽略规则，修复链接，核对材料归属与版本管理可见性。

本次允许修改文档、AGENTS、README 和文档相关忽略规则；必要时仅修正文档路径引用文字，不改变源码执行逻辑。不修改业务行为，不为文档目录引入新的运行依赖，不改写 Git 历史，不提交或推送，除非用户另行要求。

已有 LEGACY/legacy 目录不读取、不修改、不作为当前事实依据。按本轮明确授权，将旧资料放入新建日期目录；原本已标为 legacy 的顶层文件仅迁移位置，不读取或改写正文。现有业务代码、测试和已删除文件的状态保持原样。

## 7. 验收条件

- 用户能够从 README 和 docs/README 找到安装、配置、操作、入梦、恢复和故障说明。
- 开发者能够找到当前架构、所属模块机制、开发流程、验证方式与未完成工作。
- 当前正文不再包含旧实现当作现行机制、本轮排查叙事、孤立编号或阶段测试计数；当前限制和兼容行为保留。
- 各类文档按职责维护，当前说明与历史描述有清楚的时间和状态边界。
- 当前命令、键位、配置及核心流程与实际工作树核对；未知事实明确说明，不将设计意图冒充已实现行为。
- 历史性能或验证结论有环境、方法、日期与适用代码状态；缺失信息明确标注，不回填猜测。
- 所有改写或迁移材料保留完整本地原文；不读取或改写既有 LEGACY，归档迁移按明确授权执行，不覆盖既有业务修改。
- 正式导航中的本地链接、源码入口与文件名有效；可共享工程文档能被 Git 识别，私人原文和运行资料保持忽略。
- AGENTS 中的旧归属要求改为本方案，并保留先文档后代码、交互式讨论和用户沟通偏好。

纯文档整理使用链接、路径、版本管理与内容一致性检查；不为可逆的文档调整新增业务测试，也不把未执行的测试或现场验收报告为已通过。

## 8. 规范来源

本设计来自本轮逐项确认。采用本地技能的原则：`grill-with-docs`/`grilling` 的逐轮讨论，`domain-modeling` 的概念澄清与重要决策分工，`writing-for-agents` 的单一维护位置与按需读取，以及 `research` 的一手来源要求。按用户明确要求，概念定义融入现有文档，不采用技能建议的独立术语文件。`to-spec` 与 `handoff` 仅作为已阅读的格式与去重参考，本次未触发发布问题或临时交接流程。

这些技能没有规定 LOGOX 必须采用完整的通用目录结构；本设计按用户已确认的项目需要组合，不引入另一套重复维护的规范。
